Chapter 01

Foundations

An agent is fast, literal, and has no taste of its own yet. It will produce exactly what you asked for — not what you meant. Prompting is the practice of closing that gap.

Never say “build me a dashboard” and walk away.

Open a habit to read it. Every section is keyboard accessible, and search opens matching ones automatically.

Give the agent a memory

3 habits
01Write the handoff document before you need it

At the start of a build, ask for two documents: a README for humans and a short CONTEXT.md for the next agent. When a conversation gets long, ask for it to be compressed and for both documents to be updated.

Compress this conversation without losing nuance. Update the README
for a human reader and CONTEXT.md for the next agent, so a fresh
session can start with perfect context.

Why it works. An agent starts every session with an empty memory. One short file describing what the project is, where the data lives, what was tried, and what the rules are is the difference between starting from zero and starting from yesterday.

02Ask a question before asking for a change

You can ask for options without authorising any code. End the prompt with: “Don't change anything yet — I'm asking.” This is the cheapest way to explore an idea.

03Say “wait for my approval” when you want control

Without that sentence, an agent keeps editing while you are still thinking. With it, you get a proposal you can accept in one word. When you want speed, say “top fix only, no monologue, wait for approval.”

Plan before you build

3 habits
04The “deeper, not bigger” prompt

This is the highest-leverage instruction in the whole manual. Use it whenever a result feels generic or safe.

I want a deeper version of this task, not a bigger one. Before
revising: (1) what would a top professional do here that I'm not
asking for? (2) what's the rawest material they would start from?
(3) what specific methods and tools would they use?
(4) what — other than you or me — would prove the result is right?
Then revise with my feedback.

Why it works. It stops the agent adding features and forces it to raise the level of thinking. Depth is doing the same job properly. Size is adding more jobs.

05Collect the corrections first, then make the plan

When you have several complaints, say: “Write down everything I said, make a blueprint, wait.” Do not let the agent fix item one while you are still describing item six.

Take note of all my corrections first. Then, and only then, prepare
a revision blueprint. Don't change code yet.

06Work in phases, not in one giant leap

Ask for step one only, then review it, then step two. Small steps make bugs obvious and reversals cheap. Make each experiment its own commit with its own undo instruction, so one dial can be rejected without losing the others.

Direct like a designer

8 habits
07Use references, not vague adjectives

“Make the titles better” gives the agent nothing. “Number items like a catalogue — PRD-001, PRD-002 — so the label works whatever the item is” gives it something to aim at. The same goes for “a highlighter blue”, “soft edges like a real marker”, or “the feel of a well-made instrument”.

08Tell the agent where to look

You already know where the pain is. Say “check the settings screen at 390px” instead of asking it to check the whole app and guess.

09Invite pushback

“Push back if your option is better?” turns a yes-machine into a colleague. In a real build, asking for two buttons produced a reasoned argument for one; accepting it produced a better product.

10When you want speed, say so

Short prompts produce short answers. “No monologue. Top fix only. Wait for approval.” is a complete instruction when the site is on fire.

11Make the agent show you the result

“Show me locally before deploying” should be the default ending of a build prompt. A change that has been deployed before you saw it is a change you did not approve.

12Repeat, then escalate from symptom to cause

If the same complaint comes back, do not just repeat it. Say: “None of your fixes worked. Investigate the root cause.” That forces an investigation instead of another patch.

13Revert, but keep the good part

A revert does not have to throw everything away. “Go back to the earlier layout, but keep the same column width and scale the image inside it” preserves the useful decision.

14Don't let two agents write the same file

Concurrent edits to one area have to be reverted and carefully re-applied. If you run agents in parallel, give each one a separate set of files.

Make quality non-negotiable

4 habits
15Ask for evidence, not adjectives

“It should work now” is not proof. “I clicked the row, reloaded, and the new value was still there” is proof. An automated click that calls a handler directly is not a real click: it skips hit-testing, pointer events, and everything that can go wrong for a person.

Drive a real input. Ask for a genuine browser click or tap, a real reload, and the actual numbers. For a dashboard, that usually means a small script that drives the browser the way a person does — because synthetic events flatter the result.

16Protect the design system

Say what to preserve: “change this screen, keep the tokens, don't touch the other pages, no new dependencies.” Without a boundary, an agent will “improve” unrelated parts of the app.

17Demand beginner-level explanations

“Explain how this works as if I've never seen the code.” If the explanation is confusing, the design probably is too.

18Ask the agent to audit itself

Give it a checklist, not the word “review”: links, empty states, narrow screens, contrast, failed writes, and anything you told it to preserve. Also ask what is working, so the report is not one-sided.

Write the rules down once

5 habits
19Give the agent a short rulebook it reads every session

Seven short rules, kept in the project and repeated automatically, beat a long manual nobody reads:

  1. Propose, then wait. Approve a blueprint before code changes.
  2. Deeper, not bigger. Depth is doing it properly; size is adding features.
  3. The standing question. What would a top professional do here that I'm not asking for?
  4. The brief is a phone. The app will be reviewed on a phone.
  5. Measure, don't assert. Every claim has a number behind it.
  6. Drive a real input. A synthetic click proves a handler exists and nothing else.
  7. Be brief. Short answers, on request, every time.
20Keep a “do not re-litigate” list

Whenever you reject something, record one line: “Rejected: X, because Y. Do not propose again.” Otherwise the agent will innocently bring it back next session.

21Leave resume instructions for paused decisions

When you say “let's hold this”, add: “Write down that I must decide this before you continue.” Then the next session starts by asking, not by guessing.

22Write the spec before the code — and build the measuring instrument

Start a proposal with a status line: “PROPOSAL. Nothing is built. No files changed.” Give each item the headings What / Why / Cost and risk / Verified by / Must not break. Ask for the check script to be written alongside the proposal, because a claim without a way to re-check it is a rumour.

23Report the symptom in your own words, mistakes and all

“It says saved, but nothing changed” is a perfect bug report. Do not diagnose first. Say “reproduce it before fixing it”, and if the first fix changes nothing, keep looking — one symptom often hides two unrelated causes.

Chapter 02

Dashboard playbook

A dashboard is not a page with charts. It is a control room: someone must see the state of things, change them safely, and know the change stuck.

Every dashboard screen needs eight things:

  1. Data — where the rows come from.
  2. A view — a table, cards, or charts showing current state.
  3. An editor — a form to change one row.
  4. A save action — and proof the save worked.
  5. A publish action — if edits should not go live immediately.
  6. Five states — empty, loading, populated, error, saving.
  7. A narrow layout — it will be opened on a phone.
  8. A check — proof that add, edit, and delete actually happened.

If your prompt mentions only data and a view, you will get a demo, not a tool.

Build the foundation

3 rules
01Start with the data model, not the layout

Before asking for UI, answer: what objects exist, which fields each has, who may edit them, and where the data is stored.

Before writing UI, show me the data model for <thing>:
- object names and fields
- which fields are editable in the dashboard
- where data is stored and how it reaches the public view
Don't write code yet.

Keep every editable field in one list that the form, the save code, and the checks all read from. A field missing from that list is silently dropped on save — the most frustrating kind of dashboard bug, because the interface says it worked.

02Design all five states, not just the happy one

Dashboards are where “it works on my machine” dies. Ask for:

  • Empty — no data yet; what does the screen say?
  • Loading — what shows while data loads?
  • Populated — the normal view.
  • Error — what if the request or upload fails?
  • Saving / publishing — is there visible, honest confirmation?

Never show “saved” until the write has actually been confirmed. Confirm by reading the data back, not by trusting the response. A false success message is worse than no message.

03Separate Save from Publish

Decide explicitly whether an edit goes live immediately or needs a publish step. For a content dashboard, automatic private saving plus an explicit Publish action is usually safer.

A reasoned pushback from a real build: “Publish gating is worth it; a separate Save button is not. Save prevents data loss, which is the bigger risk. Publish should be explicit.” The beginner accepted it in four words: “skip Save, add Publish site.”

Lesson. Describe the outcome you want — “fail proof” — and let the agent propose where the gate belongs.

Give the publish button real states, such as idle / starting / polling / published / failed, and paint every transition on the button itself. The transition table is the guard: a double-click must not start two deploys. Cancel timers on every exit path, and give up after a few failed polls instead of polling forever.

Design for use

5 rules
04Guard against vanity metrics

Ask for numbers that prove something — items published, items in draft, last sync time, failed uploads — not decorative counts. Ask the agent to justify every number it puts on screen.

05Make it responsive and check it on a phone

Dashboards are used on laptops but reviewed on phones. Say “mobile first” in the original prompt, then verify at 390px. A control that is off-screen is a broken control, especially when there is no clue anything is hidden.

06Ask for theming and accessibility up front

Name the toggle action, not the current state. Ask for focus order, keyboard-only operation, visible focus rings, labels on every input, and an announcement when saving or publishing completes. Keep all colours in one token set; a literal colour in a component breaks the other theme.

07Name the things that must not change

List the invariants: the auth flow, the data schema, the tokens, the public view's behaviour, the size budget. Then a fix that quietly changes one is recognisable as a failure. Add: “If the fix needs more than the file set I named, stop and report. Never approximate.”

08Specify copy and budgets — never invent data

Store user-facing strings in one place so the agent cannot paraphrase them. In a demo, label sample numbers clearly as placeholders. Never let it invent handles, identities, or metrics.

Prove it works

3 rules
09Make the checks falsifiable

Reproduce first, record the result, fix, record again. If a check passes both times, it proves nothing. Also check that the harness is measuring the real app and real data — a test rig pointed at an empty stub will report green forever.

Before the fix, run <check> and record the result. After the fix,
run it again and record the result. If it passes both times, it
proves nothing. Tell me both numbers.

For a dashboard ask the agent to build hooks that prove: add → reload → row exists; edit → reload → new value; delete → confirm → gone; failed upload → clear error, no false success; mobile width → no overflow, buttons reachable; publish → the public view reflects the change.

10For a big dashboard, separate the roles

One agent edits files. A second reviews the diff against the written spec and does not edit. A third runs independent checks and does not edit. An agent reviewing its own work tends to agree with itself.

11A dashboard prompt you can copy 
Goal: Build a "Content" screen in the admin dashboard to manage <items>.

Context: It uses the same data source as the public <section>.
Follow the existing layout, tokens and auth. Fields: title, date,
image, description, published (boolean).

Constraints: No new dependencies. Don't change public pages. Keep
the design system and the current theme toggle. Model the publish
button as a state machine; prevent double-clicks.

States: Show empty, loading, populated, error and saving states.
Never show "saved" unless the write actually succeeded. Publish is
separate from the automatic private save.

Check: Verify in-browser — add, edit, delete, reload, error case,
mobile width, and real clicks (not synthetic ones). Rebuild assets.

Delivery: Show me locally first. Don't deploy.

War stories

5 failures

Five short failures that teach more than any rule.

A“It says saved, but nothing changed”

Two unrelated bugs hid behind one sentence. The form turned an uploaded file into the string "{}", so text fields saved and the image did not — the request returned 200 and the interface said “saved”. Separately, the upload route was shadowed by a catch-all, so drag-and-drop had never worked.

Lesson. A 200 response and a toast are not proof. Read the data back. When the first fix changes nothing, look for a second cause.

B“The settings screen still shows the login page”

The static host answered a missing API path with the homepage and a 200. The client helper treated that HTML as data, decided the user was not logged in, and showed login — only on the deployed site, which nobody had tested by hand.

Lesson. Verify through the same surface the user uses. “The API works” is not the same claim as “the dashboard works.”

C“Nothing happens” when pressing Publish

The fix was correct on the server, but the browser kept serving a cached old script, so the same error kept appearing. Cache-busting was a separate fix.

Lesson. When a fix appears not to work, check that it was delivered before rewriting it.

D“I changed the order, but it didn't stick”

Again two causes: the build ignored the column the buttons were writing, and nothing rebuilt the public data after an edit. The second looked exactly like the first.

Lesson. One symptom, two layers. Trace the whole path: button → write → storage → build → screen.

E“Check the settings on a phone”

Four menu items were off-screen at 390px, including the account settings. Nothing indicated there was more to scroll to.

Lesson. “Every action reachable at 390px” belongs in your acceptance criteria.

Chapter 04

The working loop

Run this every time. Step eight happens only after step five has produced evidence.

  1. 01Explore

    Ask questions. “Don't change anything yet.”

  2. 02Define

    Data model and blueprint before code.

  3. 03Build

    One small step at a time.

  4. 04See

    Show me locally, desktop and phone.

  5. 05Check

    Demand evidence, not “it should work.”

  6. 06Decide

    Approve, push back, or revert but keep.

  7. 07Record

    Commit and update the context doc.

  8. 08Ship

    Deploy only after seeing it.

One-screen cheat sheet

The whole manual in thirteen lines. Print it, pin it, ignore the rest.

  1. Give it memory — a short rulebook and handoff doc, updated every session.
  2. Ask before you build — “don't change anything yet” is free.
  3. Plan, then build — corrections first, blueprint second, code third.
  4. Go deeper, not bigger — the four questions beat “add more”.
  5. Be concrete — references beat adjectives.
  6. Invite pushback — “push back if your option is better?”
  7. Show me local — never deploy unseen.
  8. Prove it — a real click and a before/after number beat “fixed”.
  9. Protect the system — name the invariants a fix may not touch.
  10. Make it falsifiable — a check must be able to fail.
  11. Record rejections — “do not re-litigate”.
  12. Iterate without ego — small commits, easy reverts, go again.
  13. For dashboards — data model first, five states, Save versus Publish, real proof the write landed, every action reachable on a phone.
