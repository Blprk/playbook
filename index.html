Chapter 01

Foundations

An agent is fast, literal, and has no taste of its own. It produces what you asked for, not what you meant. Prompting is the practice of closing that gap.

Never say “build me a dashboard” and walk away.

Open a habit to read it. Every accordion is keyboard accessible, and search opens matching sections automatically.

Give the agent a memory

3 habits
01Write the handoff document before you need it

At the start of a build, ask for two documents: a README for humans and a short CONTEXT.md for the next agent. When the conversation gets long, ask the agent to compress it and update both documents so a fresh session loses nothing.

Compress this conversation without losing nuance. Update the README
for a human reader and CONTEXT.md for the next agent, so a fresh
session can start with perfect context.

Why it works. An agent starts each session with no memory of earlier ones. One short file — what the project is, where the data lives, what was tried, what the rules are — is the difference between starting from zero and starting from yesterday.

02Ask a question before asking for a change

You can ask for options without authorising any code. End the prompt with: “Don't change anything yet — I'm asking.” This is the cheapest way to explore an idea.

03Say “wait for my approval” when you want control

Without that sentence, an agent keeps editing while you are still thinking. With it, you get a proposal you can accept in one word. When you want speed, say “top fix only, no monologue, wait for approval.”

Plan before you build

3 habits
04The “deeper, not bigger” prompt

This is the highest-leverage instruction in the whole manual. Use it whenever a result feels generic or safe.

I want a deeper version of this task, not a bigger one. Before
revising: (1) what would a top professional do here that I'm not
asking for? (2) what's the rawest material they would start from?
(3) what specific methods and tools would they use?
(4) what — other than you or me — would prove the result is right?
Then revise with my feedback.

Why it works. It stops the agent adding features and forces it to raise the level of thinking. Depth is doing the same job properly. Size is adding more jobs.

05Collect the corrections first, then make the plan

When you have several complaints, say: “Write down everything I said, make a blueprint, wait.” Do not let the agent fix item one while you are still describing item six.

Take note of all my corrections first. Then, and only then, prepare
a revision blueprint. Don't change code yet.

1. <critique>
2. <critique>
3. <critique>
06Work in phases, not in one giant leap

Ask for step one only, then review it, then step two. Small steps make bugs obvious and reversals cheap. Make each experiment its own commit with its own undo instruction, so one dial can be rejected without losing the others.

Direct like a designer

8 habits
07Use references, not vague adjectives

“Make the titles better” gives the agent nothing. “Number items like a catalogue — PRD-001, PRD-002 — so the label works whatever the item is” gives it something to aim at. The same goes for “a highlighter blue”, “soft edges like a real marker”, or “the feel of a well-made instrument”.

08Tell the agent where to look

You already know where the pain is. Say “check the settings screen at 390px” instead of asking it to check the whole app and guess.

09Invite pushback

“Push back if your option is better?” turns a yes-machine into a colleague. In one build, a request for two buttons drew a reasoned argument for one — and the single button was the better product.

10When you want speed, say so

Short prompts produce short answers. “No monologue. Top fix only. Wait for approval.” is a complete instruction when the site is on fire.

11Make the agent show you the result

“Show me locally before deploying” should be the default ending of a build prompt. For a dashboard, that means a local URL and a screenshot of the changed screen. A change deployed before you saw it is a change you did not approve.

12Repeat, then escalate from symptom to cause

If the same complaint comes back, do not just repeat it. Say: “None of your fixes worked. Investigate the root cause.” That forces an investigation instead of another patch.

13Revert, but keep the good part

A revert does not have to throw everything away. “Go back to the earlier layout, but keep the same column width and scale the image inside it” preserves the useful decision.

14Don't let two agents write the same file

Concurrent edits to one area have to be reverted and carefully re-applied. If you run agents in parallel, give each one a separate set of files.

Make quality non-negotiable

4 habits
15Ask for evidence, not adjectives

“It should work now” is not proof. “I clicked the row, reloaded, and the new value was still there” is proof. An automated click that calls a handler directly is not a real click: it skips hit-testing, pointer events, and everything that can go wrong for a person.

Drive a real input. Ask for a genuine browser click or tap, a real reload, and the actual numbers. For a dashboard, that usually means a small script that drives the browser the way a person does — because synthetic events flatter the result.

16Protect the design system

Say what to preserve: “change this screen, keep the tokens, don't touch the other pages, no new dependencies.” Without a boundary, an agent will “improve” unrelated parts of the app.

17Demand beginner-level explanations

“Explain how this works as if I've never seen the code.” For a save form, the explanation should name the field list, the write, and the read-back in that order. If the explanation is confusing, the design probably is too.

18Ask the agent to audit itself

Give it a checklist, not the word “review”: links, empty states, narrow screens, contrast, failed writes, and anything you told it to preserve. Also ask what is working, so the report is not one-sided.

Write the rules down once

5 habits
19Give the agent a short rulebook it reads every session

Seven short rules, kept in the project and repeated automatically, beat a long manual nobody reads:

  1. Propose, then wait. Approve a blueprint before code changes.
  2. Deeper, not bigger. Depth is doing it properly; size is adding features.
  3. The standing question. What would a top professional do here that I'm not asking for?
  4. The brief is a phone. The app will be reviewed on a phone.
  5. Measure, don't assert. Every claim has a number behind it.
  6. Drive a real input. A synthetic click proves a handler exists and nothing else.
  7. Be brief. Short answers, on request, every time.
20Keep a “do not re-litigate” list

Whenever you reject something, record one line: “Rejected: X, because Y. Do not propose again.” Otherwise the agent will innocently bring it back next session.

21Leave resume instructions for paused decisions

When you say “let's hold this”, add: “Write down that I must decide this before you continue.” Then the next session starts by asking, not by guessing.

22Write the spec before the code — and build the measuring instrument

Start a proposal with a status line: “PROPOSAL. Nothing is built. No files changed.” Give each item the headings What / Why / Cost and risk / Verified by / Must not break. Ask for the check script to be written alongside the proposal, because a claim without a way to re-check it is a rumour.

23Report the symptom in your own words, mistakes and all

“It says saved, but nothing changed” is a perfect bug report. Do not diagnose first. Say “reproduce it before fixing it”, and if the first fix changes nothing, keep looking — one symptom often hides two unrelated causes.

Chapter 02

Dashboard playbook

Chapter 01 tells you how to direct an agent. This chapter tells you what a dashboard actually needs.

A dashboard is not a page with charts. It is a control room: someone must see the state of things, change them safely, and know the change stuck.

Every dashboard screen needs eight things:

  1. Data — where the rows come from.
  2. A view — a table, cards, or charts showing current state.
  3. An editor — a form to change one row.
  4. A save action — and proof the save worked.
  5. A publish action — if edits should not go live immediately.
  6. Five states — empty, loading, populated, error, saving.
  7. A narrow layout — it will be opened on a phone.
  8. A check — proof that add, edit, and delete actually happened.

If your prompt mentions only data and a view, you will get a demo, not a tool.

Build the foundation

3 rules
01Start with the data model, not the layout

Before asking for UI, answer: what objects exist, which fields each has, who may edit them, and where the data is stored.

Before writing UI, show me the data model for <thing>:
- object names and fields
- which fields are editable in the dashboard
- where data is stored and how it reaches the public view
Don't write code yet.

Keep every editable field in one list that the form, the save code, and the checks all read from. A field missing from that list is silently dropped on save — the most frustrating kind of dashboard bug, because the interface says it worked.

02Design all five states, not just the happy one

Dashboards are where “it works on my machine” dies. Ask for:

  • Empty — no data yet; what does the screen say?
  • Loading — what shows while data loads?
  • Populated — the normal view.
  • Error — what if the request or upload fails?
  • Saving / publishing — is there visible, honest confirmation?

Never show “saved” until the write has actually been confirmed. Confirm by reading the data back, not by trusting the response. A false success message is worse than no message.

03Separate Save from Publish

Decide explicitly whether an edit goes live immediately or needs a publish step. For a content dashboard, automatic private saving plus an explicit Publish action is usually safer.

A reasoned pushback worth copying: “Publish gating is worth it; a separate Save button is not. Save prevents data loss, which is the bigger risk. Publish should be explicit.” The whole decision fits in one line: “skip Save, add Publish site.”

Lesson. Describe the outcome you want — “no lost edits, no accidental publish” — and let the agent propose where the gate belongs.

Give the publish button real states, such as idle / starting / polling / published / failed, and paint every transition on the button itself. The transition table is the guard: a double-click must not start two deploys. Cancel timers on every exit path, and give up after a few failed polls instead of polling forever.

Design for use

6 rules
04Guard against vanity metrics

Ask for numbers that prove something — items published, items in draft, last sync time, failed uploads — not decorative counts. Ask the agent to justify every number it puts on screen.

05Make it responsive and check it on a phone

Dashboards are used on laptops but reviewed on phones. Say “mobile first” in the original prompt, then verify at 390px. A control that is off-screen is a broken control, especially when there is no clue anything is hidden.

06Ask for theming and accessibility up front

Name the toggle action, not the current state. Ask for focus order, keyboard-only operation, visible focus rings, labels on every input, and an announcement when saving or publishing completes. Keep all colours in one token set; a literal colour in a component breaks the other theme.

07Name the things that must not change

List the invariants: the auth flow, the data schema, the tokens, the public view's behaviour, the size budget. Then a fix that quietly changes one is recognisable as a failure. Add: “If the fix needs more than the file set I named, stop and report. Never approximate.”

08Specify copy and budgets — never invent data

Store user-facing strings in one place so the agent cannot paraphrase them. In a demo, label sample numbers clearly as placeholders. Never let it invent handles, identities, or metrics.

09Map the hidden state machines in your UI

Most dashboard bugs are not styling problems. They are unnamed states. A panel reopened during its own closing animation gets hidden by a stale teardown timer. A publish button is clicked twice and starts two jobs. A loose pair of booleans multiplies into combinations nobody designed.

Ask the agent to write the states down before it writes the UI:

Map the implicit state machines in <screen>. Before writing
code, list every named state, every legal event, and every event
that must be ignored. For <async action>, make the button the
visible state: idle / pending / success / failed. Cancel timers
on every exit path. Use a transition table, not loose booleans.
Show me the map first; wait for my approval.

Why it works. A named machine turns “nothing happens” into a specific state and event. It also gives you a test surface: illegal events become no-ops, and every transition can be checked. For a dashboard, ask for a generation token so an old teardown cannot hide a freshly reopened panel, and for an explicit failure state after a few retries instead of an endless spinner.

Prove it works

3 rules
10Make the checks falsifiable

Reproduce first, record the result, fix, record again. If a check passes both times, it proves nothing. Also check that the harness is measuring the real app and real data — a test rig pointed at an empty stub will report green forever.

Before the fix, run <check> and record the result. After the fix,
run it again and record the result. If it passes both times, it
proves nothing. Tell me both numbers.

For a dashboard ask the agent to build hooks that prove: add → reload → row exists; edit → reload → new value; delete → confirm → gone; failed upload → clear error, no false success; mobile width → no overflow, buttons reachable; publish → the public view reflects the change.

11For a big dashboard, separate the roles

One agent edits files. A second reviews the diff against the written spec and does not edit. A third runs independent checks and does not edit. An agent reviewing its own work tends to agree with itself.

12A dashboard prompt you can copy 
Goal: Build a "Content" screen in the admin dashboard to manage <items>.

Context: It uses the same data source as the public <section>.
Follow the existing layout, tokens and auth. Fields: title, date,
image, description, published (boolean).

Constraints: No new dependencies. Don't change public pages. Keep
the design system and the current theme toggle. Model the publish
button as a state machine; prevent double-clicks.

States: Show empty, loading, populated, error and saving states.
Never show "saved" unless the write actually succeeded. Publish is
separate from the automatic private save.

Check: Verify in-browser — add, edit, delete, reload, error case,
mobile width, and real clicks (not synthetic ones). Rebuild assets.

Delivery: Show me locally first. Don't deploy.

Chapter 03

Technique toolkit

Chapters 01 and 02 cover the habits and the dashboard rules. This chapter gives you the reusable moves behind them.

Thirty-two methods for getting better work out of an agent. The first eight are enough for most people. The rest are there when something goes wrong or the work gets serious.

Start with these eight

01The five-slot prompt

Goal, Context, Constraints, Check, Delivery. If one slot is missing, the agent fills it with a guess. See the template at the top.

02The colleague test

Show your prompt to someone with no context on the task. If they would be confused, the agent will be too. This is the fastest way to find an unstated assumption.

03Explain why the rule exists

“Never use ellipses” is a rule the agent may break when it conflicts with something else. “This will be read aloud, so ellipses cannot be pronounced” is a reason the agent can generalise from.

04Give the agent a role

One sentence is enough: “You are a senior front-end engineer reviewing an accessibility-sensitive dashboard.” A role focuses tone and priorities; it does not replace concrete instructions.

05Show three to five examples

Examples are the most reliable way to steer format and tone. Make them relevant to the real task, diverse enough to avoid accidental patterns, and wrap each in tags so it is clear where it begins and ends. Ask the agent to check your examples for relevance and diversity.

06Separate instructions from data

When a prompt mixes instructions, examples, and reference material, wrap each kind in its own tag: <instructions>, <examples>, <context>, <input>. Use the same tag names every time. For short single-purpose requests, plain text is fine.

07Define success before you prompt

Write down what a correct result looks like and how you would test it. Then write the prompt. If you cannot describe the test, you are not ready to delegate the work.

08Ask it to ask you first

When the brief is fuzzy, add: “Ask me clarifying questions until you have enough to start. Do not guess.” Two questions now save a wrong implementation later.

Before you start, ask me clarifying questions until you can
state the goal, the constraints, and the success test in your
own words. Do not make any changes yet.

Control the work

09Long context at the top, question at the end

With large inputs, put the documents first and the question last. Structure each document with tags and a source label. This ordering often improves answers on multi-document tasks.

10Ground it in quotes first

For document-heavy work, ask the agent to extract the relevant passages before it draws conclusions. Quoting focuses attention on the right material and makes its reasoning inspectable.

11Say what to do, not only what not to do

“Do not use markdown” leaves the desired format undefined. “Write smoothly flowing prose paragraphs, using code fences only for code” gives the agent something positive to aim at.

12Write in the style you want back

Prompt style influences response style. A terse, structured prompt tends to produce a terse, structured answer. If you want brevity, be brief yourself.

13Ask for options, then commit

“Give me three approaches with trade-offs and recommend one.” Then pick one and say “execute that one.” This separates design from implementation and stops the agent hedging.

14Invite pushback

“Push back if your option is better?” A request for two buttons once drew an argument for one, and the narrower answer was right. That is the payoff of asking.

15Run a pre-mortem

Before implementation: “Imagine this shipped and failed. List the five most likely reasons, ranked by likelihood, and say which you will guard against first.” It finds risks that a confidence-based plan misses.

16Give it a rubric and ask it to self-check

“Before you finish, score your result against this rubric: correctness, accessibility, performance, and reversibility. Report the score and fix anything below 8/10.” A rubric makes self-critique specific instead of flattering.

17Reproduce, fix, then re-measure

Insist on a before and after number. If the check passes both times, it proves nothing. This one rule catches most fake fixes and useless tests.

18Drive a real input

A synthetic click proves a handler exists. It cannot tell you whether a person can reach the button. Ask for a real browser click or tap, a real reload, and the observed result.

19Separate builder, reviewer, verifier

One agent edits. A second compares the diff against the written spec without editing. A third runs independent checks without editing. An agent reviewing its own work tends to agree with itself.

20Chain prompts instead of stuffing one

For long work, use separate stages: research, design, implement, review, verify. Pass a short structured summary between them. Each stage gets a clean context and a single job.

Think in systems

21Write the test before the feature

Ask for a failing test that describes the behaviour you want, then the implementation that makes it pass. For a save form, the test adds a row, reloads, and asserts the row is still there. Use real inputs and real data, not a stub.

22One list, many consumers

Keep editable fields, design tokens, and user-facing strings in one definition that the form, the save path, and the checks all read. A field missing from that list is silently dropped on save.

23Fence the scope with invariants

List decisions a fix may not disturb, and say: “If this needs more than the named files, stop and report. Never approximate.” A fix that quietly changes an invariant is a failed fix.

24Name the hidden state machines

Booleans multiply into unnamed states. Ask the agent to list states, legal events, and illegal events before building the UI. See the dashboard prompt for this.

25Ask the model to improve the prompt

Metaprompting is asking an agent to critique and rewrite your prompt against a rubric. It is the cheapest optimizer there is. Use the composer below to generate one.

26Ask for structured output

When output feeds another tool, specify a schema: field names, types, allowed values, and what to do when information is missing — for example {status: "ok" | "error", changedRows: number, message: string}. Free-form prose is for people; structured data is for programs.

27Version prompts like code

Store prompts in the repository, review changes, pin model versions, and keep a small set of representative tests. Prompt changes are behaviour changes and deserve the same discipline.

28Give long work a memory

For tasks longer than one context window, keep progress notes and a structured task list in files, commit often, and tell the agent to read them on resume. Prefer a fresh session that reads the files over a bloated conversation.

29Be explicit about tools

“Can you suggest changes” often produces suggestions, not changes. “Change this function” produces a change. Say which tool or action you expect, and let independent calls run in parallel.

30Calibrate effort, do not over-prompt

Many current models already plan and self-check. Piling on “think step by step”, “be extremely thorough” and “verify everything” can add latency and over-verification. Adjust the model's effort setting, or ask for brevity explicitly, instead of writing paragraphs of meta-instructions.

31Put security in the brief

Ask for input validation, no secrets in client code, authorisation on every write, and containment checks — for example, a resolved upload path must stay inside the upload directory. Security is an acceptance criterion, not a later audit.

32Make quality measurable up front

Put the numbers in the prompt: viewport widths, contrast ratio, payload limit, interaction states, keyboard support, reduced motion. “Make it accessible” is a wish; “keyboard-only operation and 4.5:1 contrast at 390px” is a test.

Chapter 06 continued

Prompt optimizers, honestly

An optimizer is anything that improves a prompt using either rewriting or measurement. The useful ones are powered by a score. Without a score, an optimizer just makes your prompt sound more confident.

Start at the free end

Ask the model itself. Paste your prompt and use the “Improve this prompt” template in the library. Ask for a rubric score, a rewrite, and an explanation of what changed. This is metaprompting and it costs nothing but a few tokens.

Provider tools. Vendors have shipped prompt generators, improvers and playgrounds — for example Anthropic Console's prompt improver (announced in 2024) and the OpenAI Playground. Features move fast; check the current docs before relying on a named button.

When you need measurement

If your problem is…Look atWhy
A lot of manual prompt editingDSPy, DeepEvalTyped tasks and metric-driven optimisation; change the program, not the wording by hand.
Regressions after a prompt changePromptfoo, openai/evalsRun a fixed set of cases in CI and fail the build when quality drops.
Many prompt versions and collaboratorsLangfuse, PromptLayer, HumanloopVersioning, environments, datasets and rollout control.
Knowing which prompt is best in productionBraintrust, Arize, LangSmith, LogfireTracing, online and offline evaluation, and controlled rollout. Check current capabilities and pricing.

How to choose

  1. Can you score the result? If not, build a small eval set first. No optimizer can help without a signal.
  2. Is the problem the prompt or the system? If the data, retrieval, or permissions are broken, a better prompt will not fix them.
  3. Do you need to own the infrastructure? Choose open-source and self-hostable before you choose a hosted platform.

A prompt optimizer is a multiplier. Point it at a good eval set and it compounds quality. Point it at a vague goal and it compounds confusion.

The working loop

Everything above collapses into one routine. Run it every time: step eight, Ship, happens only after step five, Check, has produced evidence.

  1. 01Explore

    Ask questions. “Don't change anything yet.”

  2. 02Define

    Data model and blueprint before code.

  3. 03Build

One-screen cheat sheet

The whole manual in fifteen lines. Print it, pin it, ignore the rest.

  1. Give it memory — a short rulebook and handoff doc, updated every session.
  2. Ask before you build — “don't change anything yet” is free.
  3. Plan, then build — corrections first, blueprint second, code third.
  4. Go deeper, not bigger — the four questions beat “add more”.
  5. Be concrete — references beat adjectives.
  6. Invite pushback — “push back if your option is better?”
  7. Show me local — never deploy unseen.
  8. Prove it — a real click and a before/after number beat “fixed”.
  9. Protect the system — name the invariants a fix may not touch.
  10. Make it falsifiable — a check must be able to fail.
  11. Record rejections — “do not re-litigate”.
  12. Iterate without ego — small commits, easy reverts, go again.
  13. For dashboards — data model first, five states, Save versus Publish, real proof the write landed, every action reachable on a phone.
  14. Name the states — implicit UI states become bugs; map states and events before writing the interface.
  15. Keep learning — metaprompt your prompts, version what works, and optimise only against a score.
